# Автосервис

### Сервис для записи на определенные услуги в автосервисе. Помогает компании избегать накладок по времени.
•	Автоматизировать процесс записи клиентов на услуги автосервиса.

•	Исключить пересечение записей по времени у одного сотрудника.

•	Сотрудникам будет удобнее планировать работу

# 2.Методология:
•	Разработка: Agile/Scrum - работаем по спринтам, регулярно показываем результат. 

•	Моделирование: OOAD - строим UML-диаграммы перед тем, как писать код. 

•	Сбор требований: Use Case Driven - отталкиваемся от того, что должен уметь делать пользователь.

# 3.Технологический стек
•	Backend: Python + FastAPI

•	База данных: PostgreSQL

•	Frontend: JS + React

•	Аутентификация: JWT-токены + хеширование паролей (bcrypt)

•	Ролевая модель: 	Три роли: client / employee / admin

•	Запуск: Docker + docker-compose

# 4.Ролевая модель
Все пользователи регистрируются самостоятельно и автоматически  выбирается  роль «клиент». Роль администратора через регистрацию получить нельзя: первый администратор создаётся при инициализации базы данных. Сотрудников регистрирует администратор

### Клиент (client)

Человек, который хочет записаться на услугу.

### Может:   
1.	Зарегестрироваться на сервисе
3.	Редактировать свой профиль
4.	Оставлять заявку на услугу
5.	Просматривать прайс-лист
6.	Просматривать свои записи

### Сотрудник (employee)

Человек, работающий на компанию

### Может:   
1.	Принимать заявки на услуги
2.	Просматривать свое расписание
3.	Устанавливать цену на дополнительные расходы на услуге согласно прайсу
### Не может:
1.	Просматривать чужие  расписания
2.	Накладывать записи друг на друга
3.	Изменять время уже принятой записи
   
### Администратор(admin):

Человек, управляющий компанией

### Может:
1.	Добавлять\редактировать\удалять аккаунты мастеров
2.	Добавлять\редактировать\удалять услуги и дополнительные услуги в прайс-лист
3.	Отменять записи в расписании у мастеров
4.	Просматривать расписания мастеров

# 6.1  Диаграмма классов 
### Основные классы
1.	User - пользователь системы.
•	Атрибуты: id, name, email, password_hash, role (enum: CLIENT / EMPLOYEE / ADMIN).

•	Методы: register(), login(), updateProfile(), createEmployee(), deleteEmployee().

3.	Service - услуга автосервиса.
•	Атрибуты: id, name, description, duration, price.

•	Методы: create(), update(), delete().

5.	Appointment - запись клиента на услугу.
•	Атрибуты: id, client_id, employee_id, service_id, start_time, status.

•	Методы: create(), accept(), cancel(), checkTimeConflict().

7.	 PriceItem - позиция прайс-листа, используемая для расчёта дополнительных расходов.
•	Атрибуты: id, name, price.

•	Методы: create(), update(), delete().

9.	ExtraExpense - дополнительные расходы, добавленные к записи клиента.
•	Атрибуты: id, appointment_id, price_item_id, quantity, total.

•	Методы: calculateTotal().

### Перечисления
1.	UserRole - роль пользователя:
•	CLIENT - клиент;

•	EMPLOYEE - сотрудник;

•	ADMIN - администратор.

3.	AppointmentStatus - статус записи:
•	NEW - новая;

•	ACCEPTED - принята;

•	CANCELLED - отменена.

### Связи между классами
1.	User ==>Appointment: один клиент может создать много записей, каждая запись относится к одному клиенту (через client_id).
2.	User ==>Appointment: один сотрудник может иметь много записей, каждая запись назначена одному сотруднику (через employee_id).
3.	Service ==>Appointment: одна услуга может встречаться во многих записях, у каждой записи только одна услуга (через service_id).
4.	Appointment ==>ExtraExpense: к одной записи может относиться несколько дополнительных расходов, каждый расход относится к одной записи (через appointment_id).
5.	PriceItem ==>ExtraExpense: одна позиция прайс-листа может использоваться во многих дополнительных расходах, каждый расход связан с одной позицией (через price_item_id).
6.	User ==>UserRole: каждому пользователю назначается одна роль.
7.	Appointment ==>AppointmentStatus: каждой записи назначается один статус.
### Основные правила системы
1.	Клиент может записаться только на одну услугу в рамках одной записи.
2.	У одного сотрудника не 	больше одной записи на одно и то же время.
3.	Сотрудник видит только своё расписание.
4.	Сотрудник не может изменить время уже принятой записи.
5.	Администратор может управлять аккаунтами сотрудников и услугами.
6.	Администратор может просматривать расписания всех сотрудников и отменять записи.
7.	Дополнительные расходы добавляются сотрудником на основании прайс-листа.

# 8. Описание экранов

Раздел описывает экраны веб-интерфейса системы «Автосервис» в порядке, отражающем сценарий работы: сначала общедоступные экраны, затем экраны клиента, сотрудника и администратора. Для каждого экрана указано его назначение, основные элементы и доступные действия. Интерфейс построен по ролевой модели из раздела 4: состав меню и набор кнопок зависят от роли вошедшего пользователя, поэтому одна и та же страница записи у клиента, сотрудника и администратора выглядит по-разному. Скриншоты выполнены на демонстрационных данных: услуги «Замена масла», «Диагностика подвески», «Шиномонтаж», сотрудники Иван Петров и Пётр Сидоров, записи во всех пяти статусах.

### Главная страница (витрина услуг)
Витрина доступна всем посетителям, включая неавторизованных. В шапке размещены название сервиса и меню: гость видит кнопки «Вход» и «Регистрация», авторизованный пользователь — пункты своего раздела и кнопку «Выход». Основную часть страницы занимают карточки услуг с описанием, длительностью и ценой, ниже — прайс-лист позиций для дополнительных расходов. Из витрины клиент попадает на форму записи, а сотрудник и администратор — в свои разделы.

### Вход в систему
Экран входа содержит поля «Email» и «Пароль», кнопку «Войти» и ссылку на регистрацию. Регистрация предназначена только для клиентов: роль выбирается системой автоматически, аккаунт сотрудника или администратора через открытую регистрацию создать нельзя. ### Новая заявка: выбор услуги и мастера
Запись на услугу выполняется пошаговым мастером из четырёх шагов. На первом шаге клиент выбирает услугу — карточки показывают описание, длительность и цену; длительность услуги используется дальше для расчёта времени визита. На втором шаге отображаются активные сотрудники системы; деактивированные администратором мастера в выборе не участвуют. Выбранные значения подсвечиваются, к следующему шагу нельзя перейти, не завершив текущий.

### Новая заявка: выбор даты и времени
На третьем шаге клиент выбирает дату визита и свободный слот. Календарь ограничен двумя неделями вперёд; при выборе дня интерфейс запрашивает у сервера занятые интервалы мастера и строит сетку слотов с 09:00 до 19:00 с шагом в тридцать минут. Занятые интервалы и прошедшее время показываются неактивными, поэтому конфликт расписания исключён ещё до отправки заявки; окончательная проверка выполняется на сервере.

### Карточка заявки (сотрудник)
На карточке назначенной ему записи сотрудник видит таймлайн и полный расчёт стоимости. Для принятой заявки доступны два действия: «Добавить расход» и «Отметить выполненной». Рядом с кнопкой добавления расхода выведено предупреждение: после отметки «Выполнена» итоговая сумма фиксируется и дополнить её будет нельзя. Для заявок других сотрудников карточка недоступна — сервер отвечает отказом.

### Добавление дополнительного расхода
Расход оформляется в модальном окне: сотрудник выбирает позицию прайс-листа (в списке видна цена за единицу) и указывает количество от одного до тысячи. Сумма расхода рассчитывается на сервере как цена позиции, умноженная на количество, и фиксируется на момент добавления — последующее изменение прайса не меняет уже добавленных расходов. После сохранения карточка обновляет таблицу стоимости и итог.

### Записи (администратор)
Администратор видит записи всех сотрудников и всех клиентов. Доступны те же фильтры по статусу и датам, что и в расписании сотрудника. Кнопка «Отменить» показывается только у записей в статусах «Новая» и «Принята»; для выполненной и оплаченной записи отмена запрещена — и интерфейс не показывает кнопку, и сервер отвечает отказом. Перед отменой выводится подтверждение с предупреждением, что время мастера освободится и клиент увидит статус «Отменена».

### Сотрудники (администратор)
Раздел управления аккаунтами мастеров: список с именем, email и признаком активности, поиск по имени и email. Администратор создаёт аккаунт (имя, email, начальный пароль), редактирует данные, меняет пароль и деактивирует сотрудника. Деактивированный мастер не может войти и не отображается в форме записи, но сохраняется в истории записей. Удаление аккаунта с записями запрещено системой.

### Услуги (администратор)
Каталог услуг, на которые записываются клиенты: название, описание, длительность в минутах и цена. Администратор добавляет, изменяет и удаляет услуги; изменение цены и длительности не затрагивает уже созданные записи — их параметры зафиксированы в момент записи. Услуга, используемая в записях, не удаляется.

## Прайс-лист дополнительных расходов (администратор)
Отдельный каталог позиций, которые сотрудник добавляет к заявке как дополнительные расходы: материалы и работы вне базовой услуги. Для каждой позиции задаются название и цена за единицу. Правила защиты совпадают с услугами: позиция, встречающаяся в добавленных расходах, не удаляется.

### Профиль пользователя
Общий экран для всех ролей: имя и email аккаунта, смена пароля. Для смены пароля вводится текущий пароль и новый (не короче восьми символов); после изменения старый пароль перестаёт действовать. Раздел доступен клиенту, сотруднику и администратору без отличий.
